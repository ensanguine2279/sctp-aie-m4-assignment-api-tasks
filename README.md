# Module 4 Assignment - TaskFlow Tasks API

A Spring Boot REST service that manages tasks for the TaskFlow system. It enforces token-based authorization and granular task ownership rules by verifying RS256 JWT tokens issued by the [Users Service](https://github.com/ensanguine2279/sctp-aie-m4-assignment-api-users).

## Features

- Stateless authentication using RS256 JWT signature verification (public key only)
- Token verification for mandatory issuer (`user-service`), audience (`taskflow-api`), non-expired status, and required user ID (`uid`) claim
- Granular role-based access control (`ADMIN`, `MANAGER`, `USER`) enforced with `@PreAuthorize`
- Strict task ownership logic: non-admin/manager users can only view or complete tasks that belong to their `uid`
- Task isolation: accessing a task owned by another user yields a 404 Not Found error (identical to a missing task) to prevent resource enumeration
- Task CRUD operations with strict DTO validation (`@Valid`), preventing clients from overriding immutable fields like `id` or `userId`
- Consistent JSON error response format (`message`, `timestamp`) across all status codes (400, 401, 403, 404, 415, 500)
- Dockerfile and Docker Compose setup with a dedicated PostgreSQL database
- Unit, security matrix, ownership, and web-layer tests executing against an in-memory H2 database
- Security checks in CI on every push to `main`: OWASP Dependency-Check, a Trivy scan of the container image, a gitleaks secret scan of the whole git history, and a project-specific key-leak check. Nothing is released or deployed unless they pass
- Automated releases and deployment: semantic versioning from commit messages, images on Docker Hub, rolling updates on a Docker Swarm

## Verification key (RS256)

This service **only verifies** RS256 signatures using an RSA public key (`public.pem`). It contains no private key, no token issuance code, and no password encoders. Obtain the public key generated by the Users Service:

```bash
mkdir -p ~/.taskflow/keys
# Copy or ensure public.pem exists on the host machine:
ls -l ~/.taskflow/keys/public.pem
chmod 644 ~/.taskflow/keys/public.pem
```

- `public.pem` is X.509 formatted (`-----BEGIN PUBLIC KEY-----`).
- The Tasks API's `PemKeyLoader` rejects private keys (`BEGIN PRIVATE KEY` or `BEGIN RSA PRIVATE KEY`) at startup to prevent key misuse.
- The path to the public key is configured via `jwt.public-key-path` (or environment variable `JWT_PUBLIC_KEY_PATH`).
- Missing key files or unreadable paths will halt application startup immediately.

## Quick start (Docker)

You need Docker with the Compose plugin.

```bash
# 1. Ensure the RSA public key exists at ~/.taskflow/keys/public.pem

# 2. Create your environment file from the template
cp .env.example .env
#    - Verify JWT_ISSUER_ENV (user-service) and JWT_AUDIENCE_ENV (taskflow-api) match the Users Service
#    - Optional: set JWT_PUBLIC_KEY_FILE if public.pem lives outside ~/.taskflow/keys/public.pem

# 3. Build and start the service and its database
docker compose up --build -d

# 4. Watch startup logs
docker compose logs -f task-service

# 5. Access the API with a Bearer token issued by the Users Service
curl -i -X GET http://localhost:8077/api/tasks \
  -H "Authorization: Bearer <JWT_TOKEN_FROM_USERS_SERVICE>"
```

Compose mounts `public.pem` into the container as a read-only secret at `/run/secrets/jwt_public_key`, sourced from `${HOME}/.taskflow/keys/public.pem` on the host (override via `JWT_PUBLIC_KEY_FILE` in `.env`).

To stop: `docker compose down`. Database data persists in the `tasks_db_data` volume. To purge data: `docker compose down -v`.

The Compose file defines a healthcheck for `task-db`, and `task-service` waits for it via `depends_on.condition: service_healthy`.

## Running locally

Prerequisites: JDK 17+ and a running PostgreSQL database.

```bash
export SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5433/taskflow-tasks
export SPRING_DATASOURCE_USERNAME=postgres
export SPRING_DATASOURCE_PASSWORD='<your-database-password>'
export SPRING_JPA_HIBERNATE_DDL_AUTO=update
export JWT_PUBLIC_KEY_PATH=$HOME/.taskflow/keys/public.pem
export JWT_ISSUER=user-service
export JWT_AUDIENCE=taskflow-api

# Run the Spring Boot application
./mvnw spring-boot:run
```

In PowerShell, set environment variables with `$env:JWT_PUBLIC_KEY_PATH="..."`. In an IDE, add them to the run configuration. Plain `mvn` executions do not read `.env` or Compose variables automatically, so export `JWT_PUBLIC_KEY_PATH` explicitly. The application has no default path and will refuse to start without a valid key file.

## Configuration

Every property can be defined in `application.properties` or via environment variables (Spring's relaxed binding rule: dots and dashes become underscores, upper-cased).

| Property | Environment variable | Description |
|---|---|---|
| `jwt.public-key-path` | `JWT_PUBLIC_KEY_PATH` | File path to the X.509 `public.pem` RSA key. **Required, no default.** In Docker Compose this is `/run/secrets/jwt_public_key`. |
| `jwt.issuer` | `JWT_ISSUER` | Expected `iss` claim in incoming JWTs (default `user-service`). Must match Users Service. |
| `jwt.audience` | `JWT_AUDIENCE` | Expected `aud` claim in incoming JWTs (default `taskflow-api`). Must match Users Service. |
| `spring.datasource.url` | `SPRING_DATASOURCE_URL` | JDBC URL for PostgreSQL. |
| `spring.datasource.username` | `SPRING_DATASOURCE_USERNAME` | Database connection username. |
| `spring.datasource.password` | `SPRING_DATASOURCE_PASSWORD` | Database connection password. |
| `spring.jpa.hibernate.ddl-auto` | `SPRING_JPA_HIBERNATE_DDL_AUTO` | Schema creation strategy (`create`, `update`, `none`). |
| `spring.profiles.active` | `SPRING_PROFILES_ACTIVE` | Active Spring profiles (e.g., `dev`). |

Never commit `*.pem` keys, database passwords, or `.env` files. Keep secrets in environment variables or mounted secret files.

## API

All request and response bodies use JSON format. All endpoints require a valid `Authorization: Bearer <token>` header.

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/api/tasks` | ADMIN, MANAGER | List all tasks |
| GET | `/api/tasks/{id}` | Any valid user | Get a task by ID (Owners, ADMIN, MANAGER) |
| GET | `/api/tasks/user/{userId}` | ADMIN, MANAGER, or target user | List all tasks belonging to `userId` |
| POST | `/api/tasks` | ADMIN, MANAGER | Create a new task (`201`) |
| PUT | `/api/tasks/{id}` | ADMIN, MANAGER | Update a task's details (`200`) |
| PUT | `/api/tasks/{id}/complete` | Any valid user | Mark a task as completed (Owners, ADMIN, MANAGER) |
| DELETE | `/api/tasks/{id}` | ADMIN, MANAGER | Delete a task (`200`) |

### Create a task (Admin / Manager)

```http
POST /api/tasks
Authorization: Bearer <admin or manager token>
Content-Type: application/json

{
  "title": "Deploy Tasks Service",
  "description": "Configure Docker Compose stack",
  "priority": "HIGH",
  "completed": false,
  "userId": 42
}
```

```json
{
  "id": 1,
  "title": "Deploy Tasks Service",
  "description": "Configure Docker Compose stack",
  "priority": "HIGH",
  "completed": false,
  "userId": 42
}
```

`id` is read-only and automatically generated. Client-supplied `id` values in request bodies are ignored.

### Get task by ID

```http
GET /api/tasks/1
Authorization: Bearer <user token with uid=42>
```

```json
{
  "id": 1,
  "title": "Deploy Tasks Service",
  "description": "Configure Docker Compose stack",
  "priority": "HIGH",
  "completed": false,
  "userId": 42
}
```

If user `99` sends `GET /api/tasks/1`, the response is `404 Not Found`, shielding the existence of user `42`'s task from unauthorized callers.

### Complete a task

```http
PUT /api/tasks/1/complete
Authorization: Bearer <user token with uid=42>
```

```json
{
  "id": 1,
  "title": "Deploy Tasks Service",
  "description": "Configure Docker Compose stack",
  "priority": "HIGH",
  "completed": true,
  "userId": 42
}
```

### Validation rules

| Field | Rule |
|---|---|
| `title` | Required, non-blank string |
| `description` | Optional string |
| `priority` | Required, must match `LOW`, `MEDIUM`, or `HIGH` |
| `completed` | Required `Boolean` (`true` or `false`) |
| `userId` | Required positive integer (`@Positive`) on `POST` requests |

### Errors

All error responses use a standard error structure:

```json
{
  "message": "Task with id 99 not found",
  "timestamp": "2026-10-17T12:00:00Z"
}
```

| Status | Cause |
|---|---|
| 400 | DTO validation failure (e.g., `title: Title is mandatory`), malformed JSON body, or invalid type conversion on path parameters (e.g., `/api/tasks/abc`). |
| 401 | Missing `Authorization` header, invalid RS256 signature, expired token, missing `uid` claim, or issuer/audience mismatch. Includes `WWW-Authenticate: Bearer` header. |
| 403 | Authenticated user lacks required role or attempting to view another user's task list (`GET /api/tasks/user/{userId}`). |
| 404 | Task does not exist or belongs to another user (for non-admin/manager callers). |
| 415 | Unsupported request `Content-Type` header (e.g., sending `text/plain` to JSON endpoints). |
| 500 | Internal server error. Stack traces are logged server-side and omitted from responses. |

## How authentication & authorization work

1. Incoming requests pass through `JwtAuthFilter`, which extracts the `Bearer` token from the `Authorization` header (matched case-insensitively).
2. `JwtService` parses and validates the token using the mounted `public.pem` key. It verifies:
   - Signature algorithm is strictly `RS256` (rejects `HS256` and `alg: none`).
   - Token issuer (`iss`) matches `jwt.issuer`.
   - Token audience (`aud`) matches or contains `jwt.audience`.
   - Token is within valid timeframe (`exp` / `iat` with 30 seconds clock skew tolerance).
   - Token contains a valid numeric user ID (`uid`) claim.
3. Upon successful validation, `JwtAuthFilter` constructs an `AuthenticatedUser(username, userId)` principal and Populates the `SecurityContext` with authorities extracted from the `roles` claim (only entries starting with `ROLE_`).
4. Security annotations (`@PreAuthorize`) on `TaskController` evaluate caller roles.
5. Task ownership checks are evaluated via `TaskAccessPolicy`:
   - `ADMIN` and `MANAGER` roles bypass ownership checks and can access any task.
   - Standard `USER` roles can only read (`GET /{id}`) or complete (`PUT /{id}/complete`) a task if the token's `uid` matches `task.getUserId()`.
   - Unmatched tasks return `404 Not Found`, ensuring unauthorized users cannot confirm the existence of another user's task.

## Design decisions

| Decision | Reason |
|---|---|
| **Public key verification only** | Consumers hold only `public.pem` and cannot mint or forge tokens, preventing key leaks from compromising token issuance. |
| **Strict fail-closed ownership (404 instead of 403)** | Returning 404 for tasks owned by other users prevents resource enumeration attacks where malicious users probe for valid task IDs. |
| **Mandatory `uid` claim validation** | Ownership checks rely on the numeric database ID (`uid`) issued by Users Service rather than username strings, simplifying domain mappings. |
| **Case-insensitive `Bearer` scheme matching** | Accommodates minor HTTP client header variations (`bearer` vs `Bearer`) while trimming whitespace. |
| **Separate DTOs for Create/Update** | `CreateTaskRequest` requires `userId`, whereas `UpdateTaskRequest` omits `userId` and `id`, ensuring task ownership and identity remain immutable during updates. |
| **Explicit Exception Handling in `GlobalExceptionHandler`** | Handles `AccessDeniedException` explicitly to prevent Spring Security access denials from escalating into 500 Server Errors. |

## Testing

Execute tests using Maven Wrapper:

```bash
./mvnw clean test                                   # Run all test suites
./mvnw test -Dtest=TaskControllerSecurityTest      # Run role matrix security test
./mvnw test -Dtest=TaskControllerOwnershipTest     # Run ownership verification test
```

Tests run against an in-memory H2 database (`jdbc:h2:mem:...`) and use throwaway RSA key pairs generated dynamically by `TestJwtKeys`.

| Test Suite | Focus / Description |
|---|---|
| `PemKeyLoaderTest` | Public key parsing and rejection of private key files |
| `JwtServiceTest` | Token verification, clock skew handling, missing `uid` rejection, and `aud` array contract tests |
| `JwtAuthFilterTest` | Security context population and invalid token header handling |
| `TaskControllerSecurityTest` | `@PreAuthorize` role matrix testing (8 routes × 5 caller types) verifying forbidden calls never touch the service layer |
| `TaskControllerOwnershipTest` | Task ownership verification, 404 mapping for non-owned tasks, and regression checks for task-id vs user-id confusion |
| `TaskControllerTest` | Request body validation, `@Valid` error mapping, 415/404 handling, and immutable ID enforcement |
| `TaskServiceImplTest` | Service logic unit tests with Mockito |

### Smoke test

Run `smoke-test.sh` from the project root against the active Docker Compose stack:

```bash
./smoke-test.sh --up --restart
```

The smoke test logs into the Users Service, obtains a real JWT, executes task creation, reading, completion, and listing scenarios, verifies ownership isolation across two test users, and sends forged, expired, tampered, and malformed tokens to confirm proper rejection across the stack.

## Security checks

Every push to `main` runs these checks in CI. Nothing is released, built or deployed unless all of them pass.

| Check | What it catches |
|---|---|
| OWASP Dependency-Check | Libraries with known vulnerabilities (CVSS 7.0 or higher fails the build) |
| Trivy | Known vulnerabilities in the container image: Alpine packages and the jars inside the app |
| gitleaks | Passwords, tokens and keys anywhere in the git history, including commits where they were later deleted |
| `scripts/security-check.sh` | Key files or private keys in the repository or the image, default passwords in the properties and compose files, and any token-signing code in this verify-only service |

Run the quick ones before you push:

```bash
./scripts/security-check.sh            # seconds
gitleaks git --redact --verbose .      # whole history
```

`SECURITY-CHECKS.md` describes every check, how to run all of them locally, and what was found and fixed.

## Deployment

Pushes to `main` are released and deployed automatically by `.github/workflows/ci.yml`:

1. Tests and the security checks run in parallel.
2. semantic-release works out the next version from the commit messages (`fix:` is a patch, `feat:` a minor version) and creates the Git tag and GitHub release.
3. The image is built and pushed to Docker Hub as `<DOCKER_USERNAME>/task-service`, tagged with the version, the Git tag, `latest` and the commit.
4. The stack is deployed to the Docker Swarm with `docker stack deploy`, pinned to the new image's digest, and the job waits for the rolling update to finish.

A push with only `ci:`, `docs:` or `chore:` commits runs the checks but does not deploy. The repository secrets, the swarm manager setup, rollbacks and troubleshooting are covered in `README-deployment.md`.

Before the first production deploy:

- Ensure `JWT_ISSUER` (`user-service`) and `JWT_AUDIENCE` (`taskflow-api`) match the configuration on the Users Service.
- Make `public.pem` available on the swarm and keep database credentials in the manager's `tasks.env`, never in the repository.
- Configure a reverse proxy (Nginx, Caddy, or Traefik) to handle TLS termination in front of port 8077.
- Replace `spring.jpa.hibernate.ddl-auto=create` or `update` with database migration scripts (Flyway or Liquibase) before keeping real data.

## Integration with Users Service

The Tasks API relies on the Users Service for authentication context:

| Aspect | Shared Contract |
|---|---|
| **Algorithm** | `RS256` |
| **Issuer (`iss`)** | `user-service` |
| **Audience (`aud`)** | `taskflow-api` |
| **Subject (`sub`)** | Username (lowercase) |
| **User ID (`uid`)** | Positive numeric user database ID (Mandatory) |
| **Roles (`roles`)** | Array of strings prefixed with `ROLE_` (e.g., `["ROLE_ADMIN"]`) |

If `JWT_ISSUER` or `JWT_AUDIENCE` differ between the two services, token verification will fail with a `401 Unauthorized` error.

## Known limitations

- No JWKS endpoint or dynamic key rotation: replacing `public.pem` requires mounting the new key file and restarting the service.
- Tasks cannot be transferred to another `userId` via the API after creation.
- Rate limiting is not currently implemented on task endpoints.
